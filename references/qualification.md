# Live T3 qualification recipe

Use this in a separate owner-approved disposable project. It is a repeatable acceptance recipe, not a claim these gates already passed. Store actual raw tool receipts, exact candidates and observations under that project's evidence. Never attach a test schedule or test child to an unrelated project.

## Gate 1: planning from discussion

Discuss [Tiny Notes](../examples/tiny-notes/DISCUSS.md) or another small real tool. Invoke the skill in plan mode. Require a fresh draft pack, FA/PA feature/task mapping, bounded research, separate ready implementation tracks, appropriate acceptance and first-review/full-release gates. Validate with the generated pinned validator. Confirm stop=true, no owner execution authorization, no child records and no schedule. This gate needs no timer, paid infrastructure or production system.

## Gate 2: operational runner bootstrap

After the owner's instruction to implement, confirm this T3 project's actual workspace and existing supervisor with raw project-read/configure receipts. Use bind-t3; the pack UUID and actual T3 project ID remain distinct. Confirm the selected model/options and access mode without elevating permissions. Commit pack/contracts before worktree delegation; ignored references need explicit verified absolute paths in briefs.

Make the runner preflight task include a bounded operational milestone. Before it passes, only bootstrap research/planning/test tasks within its dependency closure may be reserved. Qualify:

1. A bounded T3-owned child writes/tests a tiny owned artifact and returns its exact commit; its completion wakes this same supervisor without polling. Integrate through the supervisor.
2. A bounded disposable child demonstrates scoped cancellation/interruption and terminal reconciliation without altering unrelated work. Preserve partial work and prove no owned background process remains. A cancellation request alone is not terminal proof.
3. Local helper tests prove exclusive lease, durable unknown-result intent, no duplicate assignment, overlapping-path/resource refusal, stop priority and explicit resume. Running these tests is local protocol evidence, not a live scheduler observation.
4. Relevant native commands and owned runtime identity checks pass. For Tiny Notes this can be the local OS and browser; do not allocate infrastructure solely because another project uses it.

Record exact operational milestone acceptance and proof with milestone_id=operational/full_task_verified=false, then runner-ready. Consumers may depend explicitly on this milestone. Do not falsely verify the full preflight parent.

## Gate 3: real parallel implementation and integration

Reserve a bounded disjoint batch after stable API/data contracts. Launch the T3-owned workers according to actual tool schemas/next actions, preserve each actual receipt, and verify each child got the requested profile and isolated checkout. Observe genuine overlapping work intervals from actual task timestamps, not merely two planned task rows. Integrate and qualify the real product behavior. Keep shared schemas/dependencies/status with the supervisor. An independent reviewer gets a fresh bounded task and disjoint new evidence paths.

## Gate 4: automatic interval delivery

After operational qualification, render the bound continuation prompt. Persist one create intent; create one interval schedule bound to this supervisor with everyMs=1800000. Capture actual project, thread, enabled state, ID and nextRunAt. Record schedule receipt. No second schedule and no new coordinator.

Leave T3 and the machine running. Use ordinary work/completion wakeups; do not sleep-loop or poll the timer/children. If work finishes first, checkpoint and end the turn. The next **actual automatic interval delivery** must wake this supervisor, reread state and yield on known live/unknown work or continue only dependency-ready work. Record actual trigger/time and the guard decision. A manual scheduler trigger proves only manual delivery. The 30-minute interval means a genuine full cadence test takes at least that long; tiny product tasks do not shorten that fact.

Full preflight acceptance can now be verified at its exact candidate and preflight recorded. The first-review gate must require this full proof. If the machine sleeps, quota fails or delivery is missing, leave this gate open and report the observation; do not invent success.

## Gate 5: pause, idle stop and explicit recovery

Ask the supervisor to pause. Persist stop first; disable the exact schedule, record actual confirmation, settle/cancel child work and reconcile owned runtime. Update HANDOFF. Runtime-audit must cite a real reconciliation artifact; settlement must report no blockers. Confirm it is safe to close.

Opening T3 or the next day must not clear the pause. Verify stopped state before giving an explicit owner resume instruction. Resume in the same supervisor, reconcile real outcomes, reobserve settings/targets, record fresh preflight and re-enable the existing schedule. No stale-age takeover, reset of a live branch, duplicate worker or replacement schedule. Test a scoped restart only when no unrelated project would be disrupted; do not restart the shared T3 service just to manufacture evidence.

## Gate 6: review stop and remaining full release

Demonstrate add/list/restart persistence for the first private review. Verify the configured milestone, persist review stop, disable the timer and settle runtime. Supply exact candidate, launch instructions and remaining scope. The later delete/error/documentation/final tests remain open.

Only after the owner says to proceed use advance, keep review history, refresh preflight and continue remaining tasks. At full release require all full tasks and FA acceptance, run finish, disable the timer and reconcile runtime. Confirm no schedule/child/resource is left running accidentally.

## Result record

For each gate record passed/failed/blocked/not_run, exact candidate, commands/tool receipts, actual environment, limitations and next action. Claim T3-qualified only after these live gates pass for the tested profile/environment. A future harness/version/profile change may invalidate relevant gates. Other harnesses need the adapter matrix in portability.md; tool names alone are not enough.
