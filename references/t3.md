# T3 execution adapter

This is the primary adapter. Tool names and argument schemas below were inspected in the local T3 catalog on 2026-11-12. Discover the current tools and schema before use; they may change. Harness/system instructions prevail over this reference.

## Bind and preflight

First apply [meeting and supervisor handoff](meeting.md). The meeting prepares files and, only when the owner requests it, launches a new top-level supervisor using `t3_thread_launch` or the available equivalent. Supply the completed purpose-specific kickoff as its initial prompt and record the returned link/identity; do not run the pack inline. Use `workspaceStrategy` only according to current harness rules: independent work uses the remote default branch with `startFromOrigin:true` (local default if no remote); dependent work and required unpublished commits use their actual local base. Without a strategy, verify that the project root is the intended integration workspace. Do not create shell worktrees or hide checkout setup in the prompt. An unrelated project root is not a valid fallback for a purpose directory.

Once launched, use the existing designated supervisor for this pack. Never bind a meeting thread as the execution supervisor. Read `replan/KICKOFF.md` (or the existing adopted launch record), project/workspace identity and the actual supervisor profile with available T3 tools (`t3_environment_read`, `t3_project_read`, `t3_thread_configure`). Record actual project/thread identifiers and model options in state. Never manufacture profile observations to match requested settings. Configure only within the owner's selected settings; report unavailable models instead of substituting.

The pack's `project_id` is its own generated UUID, **not** T3's project ID. Use `bind-t3` with `{project:<raw project-read receipt>,thread:<raw configure receipt>}` to preserve both and verify the T3 project actually owns this integration workspace. It records `harness_project_id` separately. A copied or unrelated T3 project must not delegate against the pack. A settings-write response may only contain an event sequence; re-read configuration to obtain the actual observed settings.

The suggested profile is codex / `gpt-6.1-sol` / `reasoningEffort=xhigh` / `serviceTier=default`. Record another provider/model when chosen by the owner. Use permission modes actually authorized, never elevate because this skill mentions autonomy.

Before first delegation call `orchestrator_capabilities` once in the thread. Recheck only after an error or owner provider change. Verify owned test environments with actual native probes. Preflight completion wakeups, project-scoped interruption/resumption, duplicate prevention and stop behavior without disrupting unrelated projects or restarting shared services. An automatic interval delivery is distinct from manually triggering a scheduler.

Use the staged recipe in [qualification](qualification.md): operational bootstrap first, automatic interval qualification second. Do not require a verified full preflight task before the only timer capable of producing its final proof can be created. Conversely, a stored timer receipt does not verify automatic wake delivery.

## Delegate

Use `delegate_task` for the T3-owned worktree and background lifecycle. Native provider subagents are not a substitute for the explicitly selected T3 worktree isolation. Do not create shell worktrees. Commit the shared pack/contracts first and reserve a bounded batch with the helper before making calls. A reservation is persisted intent, not evidence the external agent started.

Example shape; replace values from actual capabilities and returned binding:

```json
{
  "clientRequestId": "stable-unique-project-task-attempt",
  "isolation": "worktree",
  "mode": "async",
  "role": "implementation",
  "title": "PA-06 owner login",
  "target": {
    "providerInstanceId": "actual-provider",
    "model": "gpt-6.1-sol",
    "options": {"reasoningEffort": "xhigh", "serviceTier": "default"}
  },
  "task": "Complete bounded brief text; child receives no parent history."
}
```

Full brief includes task/feature IDs, base commit, absolute integration/source paths, authoritative document paths, actual scope, owned files and exclusive test resources, prohibited shared edits, acceptance checks, runtime target, review limits, retry limit and return format. See [brief template](worker-brief.md). Never put secrets in prompts. All state operations target the integration workspace, not a worker's copied state.

Persist actual task ID, child thread ID, run ID, returned link, executed model/options and worktree metadata against its reservation. Use `attach` with a captured receipt, not estimated IDs. Returned `next` may require ending the turn for completion wakeup; obey it. Do not poll live children with status, thread reads, sleeps, monitors or watchers. Read a given thread before answering about its contents; this does not authorize polling live work.

Returned model/options describe the selected configuration; `executedModel` may be null. Record that limitation rather than inventing execution telemetry. Keep actual task lifecycle IDs separate from PA IDs. Persist all pre-reserved batch receipts before yielding; if a call was definitely never issued, resolve only that reservation with factual no-call evidence. If independent calls can be safely batched by the harness, launch the bounded batch as one orchestration and retain each outcome. Do not ignore `next` to keep launching ad hoc work.

Each new independent review/re-check is a new `delegate_task` with the actual candidate, bounded brief and any relevant findings. Do not reactivate old reviewer threads with send-message tools. Fix minor findings centrally. Cancel abandoned/replaced work with `task_cancel(taskId=...)`; preserve returned evidence and worktree results. Do not interrupt a child via top-level thread interruption.

## Single continuation

After the verified operational runner milestone and execution authorization, create exactly one persistent interval schedule:

```json
{
  "clientRequestId": "stable-unique-project-continuation",
  "bindToCurrentThread": true,
  "schedule": {"type": "interval", "everyMs": 1800000},
  "prompt": "Project-specific continuation prompt with absolute workspace and supervisor binding."
}
```

Persist intent before the external call; persist the returned schedule ID, bound thread, enabled flag and next run using `schedule-record`. Unknown create outcome blocks another schedule. It must be reconciled through actual harness evidence; do not create a replacement because a timestamp is old. The helper stores a receipt but cannot call or verify the scheduler. Store actual preflight proof and never mark it passed just because helper tests pass.

Run the project's pinned helper `continuation` command to render a prompt with its actual workspace, pack ID, T3 project/thread and selected profile. Save the returned prompt and actual raw scheduler receipt. The prompt is not a call to create a second coordinator. If creation is conclusively known not to have created a schedule, `schedule-resolve` records that fact and preserves intent history; an unknown outcome cannot use that command.

Continuation prompt must instruct the supervisor to read the existing pack/handoff/state; verify binding/profile; acquire the integration lease; obey owner stop/review; disable the exact recorded schedule on stop; yield on live/unknown children or unresolved reservations; otherwise continue ready work. It must retain model, scope, runtime, retry and publication limits. It is idle recovery, not an agent-polling mechanism or a second coordinator. Completion wakeups remain primary.

Update the known schedule using `schedule_task` with `scheduledTaskId` and only the necessary fields. `enabled=false` pauses it. Record the actual returned disabled state. On owner pause, set local stop first, then disable; a failed scheduler call leaves local stop intact and an explicit unresolved schedule, not a false safe-to-shutdown claim.

On first-review success, persist `review_status=awaiting_review` and local stop before disabling continuation and settling unnecessary children. Resuming this milestone requires explicit owner direction for the next authorized phase; ordinary pause resumption cannot clear it. The helper's ordinary resume deliberately refuses a review boundary.

Use `advance --instruction <actual owner instruction file>` only when that direction exists and work/schedule/runtime are settled. It retains the first-review history, enters the full-release stage and resets preflight. Reobserve the runner and re-enable the same recorded schedule after qualification. On complete verified release, use `finish`, disable continuation, settle runtime and hand back. The helper never treats a review stop as full completion.

## Secrets and external actions

Use T3 `request_secret` for user-supplied credentials. Do not ask for tokens/passwords in chat. Paid provisioning, publication, production mutation and contacting others require authorization for the action; local implementation authorization does not imply these. Reuse existing project-scoped resources only within their recorded ownership and permission boundaries.
